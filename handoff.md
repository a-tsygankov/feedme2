## API routes
All under `/api`. All live in production (the Phase 2a and Phase 4 rows since 2026-10-12, the Phase 5a `auth/login-*` rows since the PR #5 deploy). Everything except `health`, `version`, `auth/setup|login|refresh|test-login|login-qr` and `pair/start|check` needs `Authorization: Bearer <token>`: a house access token (data scoped to its house) for the web routes and `pair/confirm`, a **device token** for `device/*` (house and device come from the verified token, never from the body).
| Route | Notes |
|---|---|
| `GET health`, `GET version` | public (Phase 0) |
| `POST auth/setup`, `login`, `refresh`, `logout`; `GET auth/me`; `PATCH auth/pin` | house name + PIN; 15-min access JWT, 30-day rotating refresh token (60 s replay grace) |
| `POST auth/login-token-create` (Phase 5a) | device token; empty body → `{token, expiresInSec: 60}`: a one-time QR login code for the device's house. A new code deletes the device's older ones (one live code per device); only the SHA-256 is stored, bound to the pairing's `devices.token_id` |
| `POST auth/login-qr` (Phase 5a) | public, body ≤ 1 KB (413). `{deviceId, token}` → `TokensResponse` like a PIN login. One conditional `UPDATE … RETURNING` consumes the code atomically (two scans: one wins); the device must still be paired to that house with the same `token_id`. Every refusal (unknown, expired, used, other device, forgotten or re-paired device) is the same 401 `unauthorized`; a success logs `qr login` to the house's feed |
| `POST auth/test-login` | no PIN; only where `ENVIRONMENT` is `development` or `test`, else 404 (used by e2e and CI) |
| `GET`, `PATCH house` | nine settings: food unit, can size, step sizes, default hungry-after, device sleep and sync intervals, timezone |
| `GET`, `POST cats`; `PATCH`, `DELETE cats/:id` | max 8 cats, never zero after the first; soft delete |
| `GET`, `POST feedings`; `PATCH`, `DELETE feedings/:id` | list is paged by compound cursor `fedAt:id` (`cat`, `from`, `to`, `limit`); POST is an idempotent batch (≤ 100) |
| `POST logs` | client log upload (house-scoped; anonymous callers persist nothing) |
| `GET debug/logs` | merged feed for the console; filters `source`, `level`, `minLevel` (rank, Phase 2a), `device`, `since`, `limit` |
| `POST pair/start`, `POST pair/check` (Phase 2a) | public. The device sends a self-chosen `pollSecret` (32 hex); `check` serves the token only to the holder of that secret, once, plus a 60 s redelivery; then `expired`. A new `start` for the same device id replaces its pending row |
| `POST pair/confirm` (Phase 2a) | house token. 404 `pair_code_unknown`, 409 `pair_code_used` / `device_in_use`, 429 `too_many_attempts` (+ `Retry-After`) after 10 failures per 10 min per house |
| `GET devices`, `PATCH devices/:id`, `DELETE devices/:id` (Phase 2a) | house token; DELETE = forget (revoke, 204) |
| `GET device/state` (Phase 2a) | device token; one read for cats, settings and the house; `ETag`/304 (the tag covers `tzOffsetMin`, so a DST change refreshes it) |
| `POST device/feedings` (Phase 2a) | device token; idempotent batch ≤ 100; `fedAt` is clamped to now when more than 5 min ahead or before 2020 (`clamped` lists those ids; 0 is allowed before the first clock sync); 409 `id_conflict` |
| `POST device/heartbeat`, `POST device/logs` (Phase 2a) | device token; heartbeat answers `{now}`; body caps 4 KB (heartbeat), 64 KB (feedings), 128 KB (logs) |
| `GET reports/summary` (Phase 4) | house token. `from`, `to`: inclusive `YYYY-MM-DD` days in the **house** zone, inside `2000-01-01..2999-12-31`, at most 732 days; optional `cat` (lowercase uuid; a removed cat's id is allowed) and `bucket` (`hour\|day\|week\|month`; default by length: 1 day → hour, ≤ 92 → day, ≤ 400 → week, else month; `hour` covers at most 7 days). One `ReportSummary`: totals (feedings, mg, cans at the current can size, mean interval, longest gap), per cat, periods stacked by cat (week keys are Mondays), interval histogram, 7×24 heatmap (Monday first). 400 `invalid_request`, 404 `cat_not_found`; `cache-control: no-store` |
| `GET reports/export.csv` (Phase 4) | same query (`bucket` ignored). One row per feeding, oldest first: `date,time,cat,amount,unit,grams,entered_value,entered_unit,source,note` in the house zone and unit; UTF-8 BOM, `attachment; filename="feedme2-<from>-<to>.csv"`, no-store; a cell starting `= + - @`, tab or CR gets a leading `'` |
| cron `0 * * * *` | hourly housekeeping: log retention (7 d, 5 000 rows per house), expired refresh tokens, (Phase 2a) expired `pending_pairings`, and (Phase 5a) QR login codes an hour past expiry |

## Webapp routes
`/login`, `/setup`, `/qr` (Phase 5a, public: the device QR's landing `/qr#deviceId=…&token=…`; the query form still works; it moves the code into state and scrubs the URL to `/qr` before the exchange, asks first when the phone is signed in to another house, then replaces itself with `/`); behind the auth gate: `/` (dashboard), `/cats/:id` (cat history), `/reports` (Phase 4, tab bar), `/settings`; anything else redirects to `/`. `/reports` keeps its filters in the URL: `range=day|week|month|custom`, `from`, `to` (custom only), `cat`, `unit=can`; a bad or stale value falls back to this week in the house zone. ## Known limitations (Phase 5b)
Escape during `add-a-cat` closes both the tour and the cat editor. The "help unavailable" banner sits inside `#root`, so it is inert while a house Sheet is open, and it covers the update bar while shown. A pointer tap on "?" while help is open lands on the backdrop, which closes help (intended; only the keyboard reaches the button itself). The help suite proves only the branch CI takes and only the first match of a repeated test id (the cat cards); targets on other branches are untested prose. Details: the Phase 5b handoff and `docs/help/README.md`.

## Known limitations (Phase 5a)
The device's Login QR screen is not built (firmware paused); `device-sim login-qr` stands in. A QR switch from another house drops that house's refresh token locally only; it stays valid on the server until it expires (decision pending). `/auth/login-qr` has no rate limit beyond the 1 KB body cap; a guess needs a 256-bit code for a live device within its minute. Details: the Phase 5a handoff.

## Known limitations (Phase 4)
Worker CPU grows with the range: 35 000 feedings over two years measured ~11–35 ms for the summary and 40–50 ms for the CSV (node, warm), a realistic house 2–7 ms; that is over the Workers Free plan's 10 ms CPU limit, and which plan the account is on is unconfirmed. The CSV formula guard misses a cell that starts with a space before `=` or with a full-width `＝`. "Today" (the default week, the cat page's 30 days) is computed at render and does not roll over at midnight while Reports stays open. A day's feeding list shows the latest 200 feedings of that day (with a note). Details and follow-ups: the Phase 4 handoff.

## Known limitations (Phase 2b)
Manual light sleep drops the Wi-Fi association (spec §5.5 says otherwise) and the USB-CDC console: after every nap the station disconnects and rejoins with its 15 s join budget, and a requested round holds the device awake for that long (`App::kJoinGraceMs`); a paired device with no reachable network dims and sleeps, and its timer wake retries. A stuck touch INT makes light sleep return at once (nap loop; bench item). Sync makes one HTTP request per loop tick (a round spans several ticks; the fetched state applies when the round ends), each over its own TLS connection. Only the backend's own 401 (`{"error":"unauthorized"}`) unpairs; any other 401 is transient (60 s retry). Menu unpair and a backend 401 both clear the cached house state. The captive portal opens by itself only on an unpaired device with no saved credentials and restarts the device after 10 idle minutes; otherwise it opens on a Press on the Wi-Fi screen or with the knob button held through boot. The cat PNG is re-decoded on every Idle rebuild (`LV_CACHE_DEF_SIZE 0`). `WifiNetwork` is `setInsecure()` (pinning: Phase 3). Generated cat sources are 268 KB (plan cap 250 KB; ~74 KB in flash). Wokwi scenarios run in CI only (not locally) and the crowpanel build has not been flashed to hardware. Details, decisions, bench items and the should-fix-before-Phase-3 list: the Phase 2b handoff.

## Known limitations (Phase 2a)
`/pair/start` is public and replaces the pending row for that device id (a nuisance, not a takeover: the poll secret protects the token). The confirm budget is read-then-record, so parallel guesses can exceed 10, and it is per house while `/auth/setup` is unlimited (anyone can mint houses). No per-device log rate limit. Devices clamp `fedAt`, the web rejects it. Details and follow-ups: the Phase 2a handoff.

## Known limitations (Phase 1)
No rate limiting anywhere (login is slowed only by PBKDF2; `/auth/setup` unlimited; body size capped only on `/api/logs`). Access tokens stay valid up to 15 min after logout or PIN change. Feedings with `fedAt` more than 5 min ahead are rejected (a fast phone clock loses them). Deploy watch item: PBKDF2 at 100k iterations may exceed the Workers Free-plan CPU limit; check the first production login. Details and follow-ups: the Phase 1 execution handoff.
